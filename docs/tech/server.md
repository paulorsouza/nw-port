# Dedicated server for the clan

Goal: the clan (10–20 people) playing together in South Windsward, with network combat without noticeable lag,
inventory, chest, merchant, crafting and house purchase, all saved on a server in the cloud.

Server rules that every area follows (budget, ticking, AI, replication, persistence) are in
[architecture.md](architecture.md). Dated decisions, delivery logs and measurements are in
[../notes/server.md](../notes/server.md).

## Architecture

```
 client (Unreal, on each PC) ──UDP 7777 (Unreal replication)──▶ game server (Unreal dedicated, Linux)
        │                                                                     │
        └──HTTPS: login ─────────────────▶  backend (Rust)  ◀── internal API ──┘
                                              │
                                          Postgres
```

| Part | Technology | Responsibility |
|---|---|---|
| Game server | Unreal 5.8 built from source, **Server** target (Linux, no rendering) | Real time: movement, collision, combat, traversal, AI, projectiles, replication. Reuses all the current C++. |
| Backend | **Rust** (axum + sqlx), written from scratch: `nw-core` | Source of truth for what persists: clan accounts, characters, items, coins, chests, houses, recipes, chat, transaction log. Economy rules live here. |
| Database | Postgres | Characters, item instances, containers, houses, coin ledger. |
| Client | Unreal, built by each player from their own New World install | Rendering, input, prediction. No game rules. |

Flows:

- **Entry**: the client logs in to the backend (clan invite + password) and gets a token. It connects to the game
  server with the token; the server validates it with the backend and loads the character.
- **Economy action** (store in a chest, buy a house, craft): the client asks the game server. The server checks the
  physical side (near the chest or station? alive?) and calls the backend, which applies the rule in a database
  transaction and returns the new state. The server replicates it to the client.
- **Combat**: only on the game server. The backend receives the result that matters (loot, death, coins).

Why the whole server is not written in Rust from scratch: it would mean rewriting movement with city collision,
traversal, hit detection from animation (blade and root motion), AI and projectiles, and replacing the client's
networking with a custom protocol with prediction. That is months before getting back to the current state. In the
hybrid model Rust handles the persistent world, and it can grow later (several cities = several game servers on the
same backend).

nw-core API and data rules: [backend/README.md](../../backend/README.md).

### Network version

The game has its own network version (`FNWPortModule`, `NetProtocol`). Without it, a server built from engine
source refuses clients built with the installed engine.

### Client entry screen

- Login screen `FNWLoginMenu`, built from game pieces (landingscreenv2: 3-slot panel and Play; popup used as the
  login, create account and create/delete character window; name field from character creation). Generated by
  `tools/ui_build_login.py`.
- Session remembered for 30 days. Deleting a character asks for its name, as in the game. Server connection errors
  show on screen.
- Enabled by `[NW.Server] Backend=` and `Address=` in `DefaultGame.ini`, or `-nwbackend= -nwconnect=`. Without them
  the game opens straight into the arena.
- Checked with `-nwuisteps` (fill and click steps through the same path as the mouse): login, wrong password, create
  account by invite, create and delete character, Play into the city. Real keyboard typing has not been tested by a
  person.

### Character state on the server

- `UNWBackend` (HTTP) and `ANWGameMode`: ticket checked in `PreLoginAsync`, the character spawns at the saved
  position, saved periodically and on logout.
- Abilities and weapon mastery are kept by the server and replicated only to the owner.
- Position is saved only while the character is on the ground. While falling, the last good position is kept.
- Save before the character is destroyed on logout (`PawnLeavingGame`).

## Platforms

- **Client: Windows is the main platform.** The clan plays on Windows, where New World is installed. DX12 with SM6:
  Nanite, Lumen and the PSO cache on Unreal's most tested path.
- **Game server: Linux** (cloud and Docker).
- **Development: stays on Linux.** The Linux client (Vulkan SM6) keeps working for tests.
- Unreal does not build for Windows from Linux. The Windows client is packaged on a Windows machine
  ([windows.md](windows.md)). Consequences for the phases: F8 becomes the Windows installer/guide (extraction from
  one's own install + client build there), and performance tests count on Windows.

## Languages

Portuguese (pt-BR) and English (en-US), only these two. This applies to everything: text taken from the game (the
`.loc.xml` files of each language), our own screens, and server and backend messages (the server sends a key +
parameters; the client translates).

## Cloud

- Region: São Paulo (low latency for the clan in Brazil).
- One VM runs everything with `docker compose` (game server, backend, Postgres). Daily database backup.
- Options: **Oracle Cloud Free Tier** (ARM Ampere, 4 cores / 24 GB free, has São Paulo; requires building the server
  for LinuxArm64) or a paid x86 VM (AWS, GCP, Azure, Magalu Cloud; about 2–4 vCPU / 8 GB).
- Ports: UDP 7777 (game) and 443 (backend, HTTPS). No VPN.
- Capacity, measured in F0 (details in [../notes/server.md](../notes/server.md)): 10 players ≈ 0.3 core, ~530 MB and
  ~66 KB/s outbound on the game server. A VM with 2 vCPU / 2–4 GB is more than enough for the clan; bandwidth is not
  an issue.

Assets: the game server needs the cooked content (maps, collision, animations). That is your own extracted copy going
to a private machine of yours. Clients still extract each from their own install.

## Build and package the server

- Engine 5.8.3 built from source (Epic's GitHub; requires linking the Epic account to GitHub). Linux dependencies
  only. Two AutomationTool/IOS icons are generated in place so UAT compiles. Example location:
  `/mnt/jogos/UnrealEngine/src-5.8.3`.
- Server target `NWPortServer`, packaged by `tools/linux/package_server.sh` into `deploy/build/LinuxServer` (2.3 GB).
  Cooked with the installed editor, same CompatibleChangelist.
- Docker images: `deploy/build_images.sh`, then `docker compose up -d`. Secrets in `deploy/.env` (not in git).

Steps:

1. Build the server target with the source engine:
   `cd /mnt/jogos/UnrealEngine/src-5.8.3 && Engine/Build/BatchFiles/Linux/Build.sh NWPortServer Linux Development -Project=<repo>/unreal/NWPort/NWPort.uproject -WaitMutex -MaxParallelActions=6`
2. `tools/linux/package_server.sh` (cook and package), or `--skip-cook` if only C++ changed.
3. `deploy/build_images.sh` (uses `--network=host`; DNS in the default Docker build does not work on the build
   machine).
4. Start: `docker compose -f deploy/compose.yaml up -d` (stop the local nw-core on port 8090 first).

Rules:

- Packaging is heavy (compiles and cooks). One at a time, nothing heavy alongside, New World closed.
- Deploy to production or the cloud only when the maintainer explicitly asks.

## Recordings

Requirement: nothing a player saw happen is undone, and everything that touches an item goes to a log for
investigation. Three stages, all done: 1 order and log; 2 storage, crafting and ground as operations recorded before
confirming to the client; 3 shop, gems, gathering and loot.

### Stage 1: order and log

Migration 0011, `backend/src/routes/journal.rs`, `UNWBackend::Write`.

- Session: each ticket redeem opens a new character session (`session + 1`, `save_seq = 0`). Every write of bag,
  coins or storage (state, storage, market, house, NPC rewards, credits) carries `session`, `seq` and `reason`.
  nw-core applies it only if the session is current and `seq` is greater than the last one (409 `stale_write`; the
  same `seq` = 409 `duplicate_write`). A late or out-of-order write, or one from a server that crashed, never undoes a
  newer one.
- Queue per character on the game server: one write at a time, in order. With no response it retries with the same
  `seq` (1, 2, 4, 8, 16 s). `duplicate_write` becomes 208 (already written).
- Log `item_log`, append-only: each write compares before and after (bag, equipped, storage per tab, coins) and writes
  one row per difference, with a reason (`periodic`, `logout`, `shutdown`, `storage`, `craft:<receita>`,
  `refine:<receita>:<n>`, `improve:<tipo>:<item>`, `shop:<item>:<n>`, `npc_reward:...`, `city:<cidade>`). Market
  deliveries and credits are logged as nw-core actions. Query: `GET /internal/item-log` or `tools/item_log.py`.
- Periodic save every 5 s, plus on logout and when the server shuts down.
- Decimal numbers in `props` (the game's float quality, 17 digits) are read exactly (`serde_json`
  `float_roundtrip`). Without it, before and after of the same item differed in the last digit and the log showed a
  false removal and addition on every write.

### Stage 2: operations

Migration 0012, `backend/src/routes/ground.rs`, `NWOps`.

- Store, withdraw, move between tabs, rename tab, refine, craft, improve, drop on the ground and pick up from the
  ground are operations (`NWOps::Run`). The server applies the operation to the real state, copies the result and
  reverts to the previous state in the same tick (replication shows nothing). It writes to nw-core, and only then
  applies the result, shows the notices (loot, crafting result screen) and spawns the loot bag. On failure nothing
  changes and the player sees "Não foi possível gravar" ("Could not save").
- One operation at a time per character. While it writes, moving items, potion, gems, destroy, gathering, loot, shop
  and NPC rewards wait and run afterwards. The periodic and logout saves wait too. The player's Record moves to the
  recorded state (a later save never goes back to the earlier one).
- Ground in nw-core (`ground_bags`, `ground_items`): drop = bag + new loot bag in one transaction; pick up = bag +
  what remains. Overflow from a full bag (craft, refine) goes into a loot bag recorded with the operation. The loot
  bag comes back in the same place when the player logs in (until it expires) and leaves the world when the player
  logs out. When expired, nw-core deletes it and logs `ground_expired`. In the log the ground is the location
  `ground:<saco>`.
- Crafting a weapon, shield or tool requests the serial number before the roll (if the item does not come out
  signed, the number stays unused).
- Trade skill XP does not roll back on a failed write (it is not an item).

### Stage 3: patches and remaining grants

No migration.

- `PUT state` accepts `inventory_patch` (only the slots that changed: new item or null). The game server keeps the
  last recorded bag of each character (`UNWBackend::PersistedBag`) and sends only the difference, including in the
  periodic save (no change, no bag). Log and serial checks cover only what changed.
- Gathering, creature loot, F10, shop, socket/unsocket gem, destroy item and NPC rewards are recorded operations
  (`UNWInventoryComponent::Grant` opens an operation when it is not already inside one). Log reasons: `gather`,
  `loot:<tabela>`, `dev:<comando>`, `shop:<item>:<n>`, `socket`, `unsocket`, `destroy`, `npc_reward:<chave>`.
- Move and equip are not operations (they do not create or destroy items). They go into the periodic save.

## Server security

- The client sends only intents (action, bag slot, recipe). Damage, rolls, items and coins belong to the server. The
  client never has the nw-core secret.
- F10 (test commands): the server accepts them only from an admin account in nw-core (`nw-core admin <conta>`,
  `tools/linux/rede.sh admin`). Without nw-core, or in the editor's Play, they are allowed. A client without
  permission does not open the menu. Each use goes to the server log (`F10: <account/character> used <action>`, refusals as
  Warning) and to `item_log` with the reason `dev:<comando>`.
- Open (weapons area): weapon mastery (`ServerSetMastery`) and abilities on the bar (`ServerSetWeaponAbilities`)
  accept what the client sends without checking points or whether the ability belongs to the weapon. General RPC rate
  limit.

## Phases

Each phase closes in a testable state. Local test: dedicated server + several clients on the same machine, with
`Net PktLag=80 PktLoss=1` to simulate the internet.

### F0: real dedicated server (done)

- Unreal 5.8.3 built from source.
- `NWPortServer` target, cooked for Linux, Docker image; starts locally and accepts 3 clients.
- Measure CPU/RAM/bandwidth with 10 clients (test bots that walk and attack).

Tested with `NW_SERVER=pacote tools/linux/net_test.sh 3` (3 characters log in and save, intruder refused) and
`NW_SERVER=docker tools/linux/net_test.sh 10` (`-nwbot` walks and attacks).

### F1: Rust backend (done)

- `nw-core` project (axum, sqlx, Postgres, migrations): clan accounts by invite, login, characters.
- Game server: validates the token on connect, loads and saves the character (position, health, weapon, abilities).
- Game start screen (login, choose character, enter).

### F2: smooth network (done)

- Actions with prediction: the client plays the hit immediately; the server confirms by prediction number or refuses
  and the client undoes it.
- Name plates and health over players.
- Death screen from the game with Respawn (goes to the city starting point; a dead character cannot move).
- Chat: Area/System, Enter, limit 225 characters and 5 messages per 5 s, `/ajuda` commands.
- Internationalization pt-BR/en-US everywhere.
- Group: up to 5. Commands `/convidar` `/aceitar` `/recusar` `/sair` `/g` (and in English `/invite` `/accept`
  `/decline` `/leave`). Invite valid for 60 s, leadership passes on, members do not hurt each other, panel with the
  game's member bar (grouphud), ally names in blue.

### F3: items and inventory (done)

- Item database from the game's datasheets (subset: weapons, shields, armor, potions, food, materials), loaded in the
  backend; item instances in Postgres.
- Game screens: inventory and equipment; equip a weapon from the inventory.
- Loot from the Lost (coins and materials).

What was delivered and the polish left at the time: [../notes/server.md](../notes/server.md).

### F4: complete Windsward

Only the Windsward territory, complete, before any other region. Steps in
[../game/world/windsward.md](../game/world/windsward.md): region terrain, gathering (ore, plants, alchemy, wood),
POI creatures, a living city (NPCs, interaction with E, chest, merchant, teleports) and loot chests.

### F5: crafting

- Windsward city stations with recipes from the datasheets and the game's crafting screen. Materials come from F4
  gathering.

### F6: houses

- 23 addresses in South Windsward; purchase through the game's screen; owner, guests, house chest.

### F7: production

- Cloud deploy, HTTPS, backups, logs. Admin tools (Rust CLI: give items, ban, reset house).

### F8: clan onboarding

- `tools/setup.sh` end to end (extraction from one's own install + client build) and a short guide.
- Evaluate loading assets at runtime, so the client ships without assets and each player only extracts.

## Out of scope for now

Regions other than Windsward, quests, factions, house decoration, instanced interiors, PvP, anti-cheat.

## Risks

- Building the engine from source: hours of build and about 150 GB of disk.
- Action prediction (F2) is the delicate part of "smooth".
- Onboarding 10+ people: each needs New World installed, Unreal, and space for the extraction.
- Free Tier ARM: cross-compiling for LinuxArm64 and instance availability in the region.
