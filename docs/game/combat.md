# Combat rules

Rules and numbers of New World combat that apply to every weapon. Weapon-specific data lives in
[weapons/](weapons/README.md). The procedure to bring a weapon into the port is in
[../tech/weapon-porting.md](../tech/weapon-porting.md). History of these rules: [../notes/combat.md](../notes/combat.md).

Principle: numbers, windows and animations come from the game data. The port code only applies the rules.

## Evidence

Each rule carries one of these marks:

- **data**: value read directly from a table, slice, actionlist or `.adb`.
- **inferred**: deduced from a field name, structure or consistency between values. No game code was read.
- **code**: confirmed in client code (Lumberyard reference source or the game client).
- Reverse-engineering grades: **C** = code read, **R** = reflection or data parser, **H** = hypothesis.

A fact graded C or R outranks older readings of the data and the current port code.

Structured numbers: `extract/research/combat_rules.json` (generated by script, read only).

## 1. Action flow

Resolved by reverse engineering. Applies to every weapon.

- **Chaining.** The player's combo comes from the `CAGE-TransitionInstant` / `CAGE-TransitionBuffered` procclips in
  the fragment's `.adb` (`Input`, `BackTicks`, `Condition`, `NewFragment`/`NewAction`), not from actionlist
  conditions.
- **Exit.** An action ends by its `DeactivationCondition` (usually `IfFragmentDone ExitOffsetSeconds`), never by the
  end of the animation.
- **Interruption.** Defined by the `.grid` (`Never`/`Always`/`Sometimes`).
- **Windows.** The `CAGE-Named` procclip turns a marker on by name. Parameters inside `<Conditional Name>` apply
  inside the window; otherwise `<Default>` applies.
- **Animation-driven movement**: `AnimationDrivenMotion`.
- **Turning**: linear or exponential, `1 − (1 − r)^(30·dt)`.
- **Homing** of an attack: procclip `Homing` with radius, angle, `MoveToDistance`, `MaxMoveDistance`,
  `MoveToDuration`.
- **Reaction**: the first entry of the reaction table that matches the hit's `PowerLevel` and side. Knockback and
  hit stun are in frames of 1/30 s. Hit stop does not exist.
- **Stamina**: 100 max, regeneration 33.33/s, dodge 45 (50 for the slow roll), block 10.

## 2. Camera shake

### Columns

`DT/javelindata_camerashake.datasheet.json` has the same columns as CryEngine's `IView::SShakeParams`
(`LY/CryCommon/IViewSystem.h`, `LY/CrySystem/ViewSystem/View.cpp`). Meaning from the Lumberyard code (data):

| Column | Meaning |
|---|---|
| `ShakeShiftX/Y/Z` | Camera offset in meters, camera axes (X right, Y forward, Z up). |
| `ShakeAngleX/Y/Z` | Rotation in radians (`Ang3`). |
| `FadeInDuration`, `SustainDuration`, `FadeOutDuration` | Envelope in seconds. Total = sum of the three. |
| `Frequency` | **Period**, not Hz: seconds between two random targets (`nextShake = frequency`). |
| `FlipVec` | Flips the sign at each target. Full oscillation = 2 × `Frequency`. |
| `Randomness` | Extra noise = `Randomness` × mean of the axis magnitudes. |
| `ShakeChannel` | `shakeID`. A new shake on the same channel restarts the previous one. |
| `IsSmooth` | Linear envelope passed through smoothstep `(3 − 2d)·d²`; cubic interpolation between targets. |
| `Permanent` | Ignores `SustainDuration`. |
| `UpdateOnly` | Only updates the frequency of a running shake. |

The cvar `c_shakeMult` multiplies the amplitude. The game has `g_cameraShake` (on/off) and the player option
`Hud.LocalPlayer.Options.Controls.CameraShake` (binary strings).

### IDs used in combat

| ID | Offset (m) | Angle (rad) | Fade in / sustain / fade out (s) | Total (s) | Period (s) | Channel |
|---|---|---|---|---|---|---|
| `Small` | 0.01 / 0.01 / 0.01 | 0 / 0.005 / 0 | 0 / 0.1 / 0.1 | 0.2 | 0.015 | 1 |
| `Large` | 0.04 ×3 | 0.01 ×3 | 0.1 / 0.2 / 0.1 | 0.4 | 0.03 | 2 |
| `Small_short` | 0.02 ×3 | 0 | 0.1 / 0.15 / 0.1 | 0.35 | 0.03 | 3 |
| `Large_short` | 0.02 ×3 | 0.005 ×3 | 0.05 / 0.1 / 0.05 | 0.2 | 0.015 | 4 |
| `Large_long` | 0.04 ×3 | 0.01 ×3 | 0.1 / 0.25 / 0.1 | 0.45 | 0.03 | 5 |
| `WH_Hit_L1`..`L4` | Y 0.015–0.03, Z 0.015–0.03 | Y 0.003–0.018 | 0 / 0 / 0.2–1.0 | 0.2–1.0 | 0.03–0.08 | 7 |

All have `FlipVec=1`, `IsSmooth=1`. All 40 IDs are in the JSON.

IDs that appear in the damage tables and **do not exist** in the shake table: `Medium`, `Smal`, `Large_l`, `1`, `0`,
`0.2`, `Small ` (with a trailing space). The binary has the message `GetCameraShakeData(...) failed`. Expected
result: no shake (inferred). Lowercase IDs (`small`, `large`) appear in procclips; it is not confirmed whether the
lookup ignores case.

### Whose camera shakes

Damage table columns (names from the binary; role inferred from the name):

| Column | Camera that shakes | When |
|---|---|---|
| `CameraShakeID` | attacker | hit landed |
| `TargetCameraShakeID` | target | hit landed |
| `BlockCameraShakeID` | attacker | hit blocked |
| `BlockTargetCameraShakeID` | blocker | hit blocked |
| `CritCameraShakeID` | attacker | critical |
| `CritTargetCameraShakeID` | target | critical |

- The player table (`javelindata_damagetable`) only has the `Crit*` columns. Sword and Shield: `Large_short` in
  both. A normal sword hit does not shake the camera (data: column absent).
- AI: `TargetCameraShakeID` and `BlockTargetCameraShakeID` = `Small` in most rows (2200 and 1792 rows). Damned:
  `Small` in all three target columns.
- Outside the damage table: the `ShakeCamera` procclip in the ADB (`CameraShakeID` + `CameraShakeRange` in meters).
  The sword does not use it; hammer, flail and abilities do (for example `WH_Swing_Light` on the hammer heavy).

## 3. Knockback

### Columns

| Column | Meaning | Evidence |
|---|---|---|
| `ImpactDistanceY` | Meters along the hit direction. Positive pushes away from the attacker; negative pulls (`Attack_Force_Grab`, Y = −1). | inferred |
| `ImpactDistanceX` | Lateral meters. Positive = attacker's right (`1H_Flail_Ability_Charge_PushNoDmg_Right` = +2, `_Left` = −2). | inferred |
| `ImpactDistanceZ` | Meters up (`Damned_Priest_BlastAway_Spell` 0.75; `Attack_Force_Grab` −2). | inferred |
| `ImpactDecayRate` | Decay factor of the knockback speed, 0 to 1. | inferred |
| `Block*`, `Crit*` | Same set for blocked hits and critical hits. | data |
| `UseAttackerPosForReaction` | True: direction = attacker→target. False: hit direction. | inferred |

Distribution of `ImpactDecayRate` over the 3534 rows with `ImpactDistanceY ≠ 0` (all tables): 0.8 in 3077; 0.85 in
95; 0.75 in 60; 0.7 in 46; 0 in 28; 1 in 5 (data).

### Scales

- Target: `DamageReceiverComponent.m_impactdistancescale`. Player 1.0; `damned_grunt` 1.2; 539 slices with 1.0, 96
  with 1.2, 2 with 0 (data, `SL/`).
- Reaction: `ReactionMotion` in the actionlist. Player `Scale=1.0`. Promoted elite AI `PushBackScale=0.15` (data,
  `NPC/damned/cage/damned_reaction.actionlist`).
- A hit that causes no reaction: action `Pushable` with `UsePushNoDecay=true`, lasting 0.4 s (data,
  `CAGE/playeractions_reaction.actionlist`).

### Curve (client code)

- Displacement up to time t of the reaction: `s(t) = D·(1 − r^(30·t))`, with t capped at the reaction duration. If
  the reaction ends first, the target moves `D·(1 − r^(30·T))`, not the full `D`.
- `r ≈ 0`, `r ≈ 1` or a reaction without duration: everything in the first frame.
- `ImpactDecayRate ≤ 0`: moves to a position the server writes into the hit (no source for that position).
- Axes: Y along the hit, X to its right, Z up. `PushBackScale` only reduces the forward-pointing part.
- Port rule id: `combate.empurrao_curva`, applied in `UNWCombatComponent::Push`.

## 4. Hit stun

### Unit

**Frames at 30 fps** (1 = 1/30 s). Confirmed in the `CHitStunContext` code: the reaction lasts the start of the
`HitStun` procclip + `HitStun/30`, and the rest of the fragment plays at speed `(duration − start)/(HitStun/30)`,
clamped to (0.001, 3]. The port reads the procclip start from the `.adb` (column `HitStunStart` of the reaction
actions).

Supporting data:

- In reactions `r_R1`..`r_R3` the `HitStun` procclip starts at 0.2 s (0.183–0.2 in 1254 of 1290 occurrences, all
  ADBs; data, `ADB/`).
- The `CanStun` markers fall at R1 0.433 s, R2 0.767 s, R3 0.967 s (`ADB/player/player_1h_melee.adb`).
- With frames at 30 fps, `0.2 + HitStun/30` passes those markers for typical values (R1 15 → 0.70 s; R2 25 →
  1.03 s; R3 30 → 1.20 s). With hundredths (0.35 s; 0.45 s) the reaction would end before its own markers.
- All Mannequin times are multiples of 1/30 s.

Port rule ids: `combate.quadros_por_s` and the `HitStunStart` column (code).

### `_AI` columns

They apply when the **target is AI**. Value 0 = no override, use the normal column. Inferred:

- Only the player table has `_AI` columns. AI tables do not.
- `1H_Sword_Attack1`: `PowerLevel` 0, `PowerLevel_AI` 1; `HitStun` 15, `HitStun_AI` 18.
- `OH_Shield_Attack_Bash`: `PowerLevel` 3, `PowerLevel_AI` 0. If 0 were an override, the shield would not knock
  down AI.
- `DT/javelindata_aileveldisparity`: with the AI 10+ levels above, the player's hit becomes `AdjustedPowerLevel` 1
  and `AdjustedHitStun` 20 (data). Player PL and hit stun against AI can be adjusted per target.

### Hit stop

`g_hitStopTime` = 0 by default and no `.cfg` changes it (code): **the game has no hit stop**. The port has none
either (`combate.hit_stop_s`).

## 5. Power level and stagger

### PowerLevel is a reaction category

It is not force against poise. Each value picks an animation in the reaction table.

Player target (`CAGE/playerreactiontableharness.actionlist`, data):

| PL | Reaction |
|---|---|
| 0 | `r_R0` additive, does not interrupt. Becomes `r_R2` if `GRIT_Broken`. |
| 1 / 2 / 3 | `r_R1` / `r_R2` / `r_R3` directional (F/B/L/R) |
| 4 | `r_R4` (knockdown) |
| 5 | `r_R4_F_Overhead` |
| 6 | blocked: `r_B0_Break`; not blocked: `r_R3` |
| 7 / 8 | `r_R4_F_Crumple` / `r_R4_F_Stumble` |
| 9 | `r_R2_*_Disarm` |
| 10 | `r_R1` with stun breakout (`StunBreakoutIncrement`) |

Player rules (`CAGE/playeractions_reaction.actionlist`, data):

- Blocked and stamina > 0: `UpperBodyReaction` (`r_B0`), torso only, no interruption.
- Blocked and stamina reached zero on this hit: `r_B0_Break` (guard break).
- 1 ≤ PL < 4, not blocked: full `Reaction`, interrupts, clears attack inputs.
- Grit active: only the `Stun` status interrupts. The hit becomes `r_R0`.
- `Stagger_Resisted`: `r_R0`.
- Player weapons against players: sword light and heavy have PL 0. They do not interrupt another player (data,
  `javelindata_damagetable`).

AI target, damned family (`NPC/damned/cage/damnedreactiontableharness.actionlist`, data):

| PL | Not blocked | Blocked |
|---|---|---|
| 0 | `r_R1` | `r_B1` |
| 1 | `r_R1` | `r_B1` |
| 2 | `r_R2` | `r_B2` |
| 3 | `r_R3` | `r_B3` |
| 4 | `r_R4` | `r_B3` |
| 5 / 8 | `r_R4_F_Overhead` / `r_Stun` | — |

Damned AI rules (`NPC/damned/cage/damned_reaction.actionlist`, data):

- `Solo`, `Solo-`: a `Light` hit (column `AttackType`) gives a full-body reaction.
- `Heavy`: reaction for `Solo`, `Solo-`, `Solo+`, `Named_Solo`, `Named_Solo+`.
- `Ability` with PL ≥ 1: always a reaction.
- After a full reaction: status `AI_Reaction_Limiter` for 2 s. During it, light hits only give an additive
  reaction (anti stun-lock).
- `Boss`, `Raid*`, `EliteBoss`: no reaction.
- Grit active on the AI blocks reactions, except stun.

### Stagger resistance

Source: `GritComponent.m_defaultstaggerresistrating` in the slices (data).

| Who | Rating |
|---|---|
| Player | 0 |
| `damned_grunt`, `damned_axeman` | 20 |
| `boar`, `wolf_*` | 10 |
| All NPC slices | 20 in 398, 0 in 113, 10 in 76, 30 in 8 |

The binary has the fields `staggerResist`, `staggerResistMod`, `totalStaggerDamage`, `ELSRM` in the
`GritComponent`. Inferred rule:

- Stagger damage = `BaseStaggerDamage` (weapon) × `StaggerDmgModifier` (row) × `CritStaggerDamageMultiplier` 1.5 on a
  critical (weapon).
- Resistance = rating × `StaggerResistModifier` of the row of the attack **the target is performing** × equip load
  multiplier (all 1 today).
- Damage < resistance → `Stagger_Resisted` → only `r_R0`.

Reading of the columns under this rule:

- `StaggerDmgModifier`: scales the hit's stagger damage. Sword light 0.4, heavy 1.5, charged heavy 2.4.
- `StaggerResistModifier`: in AI rows, the stagger armor during that attack. Damned light 0, heavy 1;
  `Reaction_Breakout` 10; wolf `Attack_02_Lunge` 1.6.
- Example: sword light against a standing damned = 36 × 0.4 = 14.4 < 20 → resisted. Heavy = 54 > 20 → reacts.
  Against Boar/Wolf (10) the light hit gets through.

### Player grit

`GritComponent` in the player slice (data): `m_min` 1000, `m_initmax` 10000, `m_maxnohittime` 30,
`m_setnoreactionwhenactive` true. Turned on by the `ActivateGrit` procclip in fragments (heavies, some abilities;
condition `GRIT_On_Basic_Attacks` for lights with a perk). It breaks by accumulated damage (lore text). Unit of the
values 1000/10000 has no source.

## 7. Block

### Absorption and arc

- Absorption: `BLA*` = 1 on all player weapons and shields. A frontal block absorbs 100% of the damage (data in the
  column; use inferred). `BlockAbsorptionModifier` per hit: 1, or 1.2 on sword lights.
- Arc: 180°. The player has `m_ishitfrombehindminangle` = 90°; a hit from behind is not blocked (inferred).
- `Unblockable` = True: cannot be blocked (11 rows in the player table).
- The block is active only inside the animation's `BlockActive` window (RE).

### Stamina lost per blocked hit (inferred)

```
loss = BlockStaminaDamage(attacker's weapon) × BlockStaminaDmgMod(row) × max(1 − BlockStability/100, 0.1)
```

- `BlockStaminaDamage` and `BlockStability`: `DT/javelindata_itemdefinitions_weapons` (data). Tooltip names:
  "Block Stamina Damage" and "Blocking Stability".
- 0.1 = `DamageReceiverComponent.m_blockstabilitymin` (data).
- Weapon without the attribute requirement: `BlockStability` −50% (`CAGE/playeractions_block.actionlist`, data).

| Weapon | BlockStaminaDamage | BlockStability |
|---|---|---|
| `SwordT2` | 36 | 22 |
| `HatchetT2` | 30 | 21 |
| Round shield `1hShieldAT2` | 54 | 30 |
| Kite shield `1hShieldBT3` | 48 | 40 |
| Tower shield `1hShieldDT4` | 42 | 50 |
| AI `1hSwordT2Damned` | 100 | 15 |

Examples against the round shield (30): sword light 36 × 0.4 × 0.7 = 10.1; heavy 37.8; charged heavy 60.5.
Damned light (0.1) 7.0; `Damned_1H_Melee_Primary` (0.35) 24.5; heavy (0.6) 42.

Block cost: reverse engineering lists block = 10. The data reading did not find where it is charged: the `Block` = 10
cost of `javelindata_staminacosts_player` and `BlockStaminaCost` = 0.8 of the player vitals are not charged by any
actionlist.

### Guard break

- Stamina reaches zero on a blocked hit → `r_B0_Break` + status `ExhaustedState_BlockBreak` (data).
- `BlockPowerLevel` 6 breaks through the reaction table (data).
- No block with stamina 0 or while exhausted (data, conditions of `Block_UpperBody`).

### Stamina while blocking (data, `CAGE/playeractions_block.actionlist`)

- Raising the guard (`Block_UpperBody_Raise`): regeneration off.
- Guard active: regenerates at the block rate, 10/s (`m_blockregenrate`).
- On release: 1 s delay before regeneration resumes.

Reverse engineering states the rule as: regeneration off while blocking; back 1 s after release. (unclear in the
original whether the 10/s block rate applies on top of that; the data reading above says it does.)

### Exhaustion

Reverse engineering (C/R): exhaustion is an effect of 10 s (no dodge, sprint −15%) and ends with stamina ≥ 1.

Data reading of `CAGE/playeractions_global.actionlist`, action `Exhausted` (superseded where it conflicts with the

- Enters at stamina ≤ 0%.
- Exits at stamina = 100%.
- Status `ExhaustedState` / `_DodgeDeplete`: `NoDodge`, sprint −15%. `_BlockBreak`: `NoDodge`.
- Exhausted: no block, no dodge. Attacks normally: the action `Attack_Exhausted` (rows `1H_Attack_Exhausted`,

### Equip load

all bands. Damage: light +15%, heavy −15%. The dodge fragment depends on the equip load
(`ActionConditionEquipLoadCategory` in `playeractions_dodge.actionlist`): light → `Dodge_Roll_Fast`, medium →
`Dodge_Roll`, heavy → `Dodge_Roll_Slow`.

The clip `PayStaminaCost` with `CostID=Stamina_Delay` (cost 0, `payOverTime`) covers the attacks. Effect not
confirmed.

## 9. Damage and mitigation

### AI

- Physical mitigation 0.35 and elemental 0.35 in 6041 of 7408 vitals rows. Cap 0.9
  (`MaxDefenseMitigationPercent`). Lost in general 0.35 (data, `DT/vitalstables/`).
- Base damage: `vitalsleveldata[Level].BaseDamage × DamageMod (vitals) × CategoryDamageMod` (inferred from the
  structure). Level 5: 230.9; level 10: 337.6. Category: `Solo` 1.0, `Solo-` 0.6, `Solo+` 1.2, `Named_Solo+` 1.25,
  `Elite` 1.4.
- AI 6+ levels above the player: +20% to +150% damage and armor (`javelindata_aileveldisparity`, data).

### Player

- Weapon base: Sword 64, Hatchet 67 (`BaseDamage`).
- Attributes: `1 + ScalingStrength × ModifierValueSum(STR) + ScalingDexterity × ModifierValueSum(DEX)`. Sword
  0.0085 STR, 0.0065 DEX (inferred; `ModifierValueSum` in `javelindata_attribute*.json`).
- Gear Score formula and player armor mitigation formula: no source in the data. Only the Gear Score band is in the
  client (`itens.gs_faixa`); see [items.md](items.md).
- Base health 856 (`HealthBaseMax` of the `Player` vitals); +40 per Constitution point above 5
  (`javelindata_attributeconstitution`).

Order of terms: `base × attributes × GS × DmgCoef × (critical | headshot) × (1 + bonus) × (1 − mitigation)`.

### Port damage scale

The port uses Sword = 100 as the damage scale (the game uses 64). A weapon's `BaseDamage` in the port = game damage ×
100/64.

## 10. Port design rules

- **Server-authoritative.** The server decides hit, damage, stamina and death. The client only predicts animation
  and movement.
- **C++ for rules, Blueprint for animation and tuning.** `UNWCombatComponent` in C++ (state, stamina, damage,
  replication). Anim Blueprint and Character Blueprint stay in Blueprint. No GAS.
- **Game data in DataTables.** CSVs generated from the `.datasheet` and `.adb` files, imported into Unreal. Changing
  a number does not require a recompile.
- **Rule values from reverse engineering** enter the code with their own value (constant or
  `FNWRules::Num("id", value)`).
- **Movement.** CharacterMovement. With a weapon drawn the character turns with the camera (strafe). Walk 1.65 m/s,
  run 4 m/s (blend space values), sprint costs no stamina.
- **Attacks.** Light: combo whose next swing starts when the `CanTransition` curve turns on; the input is buffered
  until then. Heavy: charged by holding. Sprint attack. During `Homing` the character turns toward the target or
  camera. Root motion comes from the montage.
- **Hit detection.** On the server, while `WeaponTrail` (or `DamageWindow`, when present) is on: capsule sweep from
  blade base to tip between the previous and current frame. One hit per target per swing (per damage key when a
  montage has several damage windows).
- **Dodge.** Direction from input (F/B/L/R). Invulnerable during the `Invulnerability` window (0–0.5 s). Cancels
  attacks in the `CanDodgeCancel` windows.
- **Death.** Health 0 → `Death`, optional ragdoll, respawn at the start point after a few seconds.

Example data per source (Sword):

| Data | Origin | Example (Sword) |
|---|---|---|
| Damage coefficient, type, hit stun, block stun, power level, knockback | `javelindata_damagetable` | `1H_Sword_Attack1`: coef 1.0, Slash, stun 15, block stun 10, knockback 0.5 |
| Stamina cost | `javelindata_staminacosts_player` | dodge 45, block 10, attacks 0 |
| Windows per attack | `ProcLayer` of the `.adb` → curves on the sequences | light attack 1: trail 0.31–0.43 s, dodge cancel from 0.50 s, chains at 0.83 s |
| Dodge invulnerability | `.adb` (`Invulnerability`) | 0–0.5 s |

| Sounds per attack and footsteps | `.adb` (`Audio`) + `.animevents` + `extract/audio/sfx_index.csv` | `Play_RHSword_Atk_PrimA1` at 0.13 s |
